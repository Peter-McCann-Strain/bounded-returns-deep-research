**Status:** pre-registered BEFORE the paid E9 full-curve generation + GPT-5.2 judging run.
**Surrogate authority:** `reports/RESEARCH_PLAN_2026H2.md` §E9 SCALE-CURVE (priority 7.5),

**Builder (post-judge, write-only in build phase):** `scripts/build_e9_scale.py`

## Hypothesis

Holding the research **architecture** fixed (P0, P1, P4) and the search backbone fixed
(SEARCH_MODEL = gpt-4o-mini, the corpus value), and varying ONLY the **generation
backbone** along a capability ladder, the marginal quality return to orchestration
(the gap between a heavier pattern, e.g. P1/P4, and the P0 baseline at the SAME backbone)
will move with backbone capability in a **measurable, fittable** way.

Directional sub-hypotheses (registered, not assumed):

- **H1 (returns shrink with capability):** the orchestration premium
  `Δ(arch) = score(arch) − score(P0)` at fixed backbone is **non-increasing** in backbone
  capability — i.e. as the backbone gets stronger, scaffolding buys less. (This is the
  "bounded returns to orchestration" headline in the long-form regime.)
- **H2 (AdaptOrch convergence):** consistent with the AdaptOrch convergence law
  (arXiv 2602.16873) extended to long-form research, the per-tier curves
  `score(arch, tier)` **converge** as capability rises (between-arch variance at the
  top tier < between-arch variance at the bottom tier).
- **H3 (matched-budget control survives):** under a **matched-budget-per-tier** control
  (equalising token/cost budget across arches within a tier, not just across tiers), any
  residual P1/P4 > P0 premium at the lower tiers **persists** rather than collapsing to a
  pure compute artefact (this is the disentanglement guard Paper 1 already applies to the
  gpt-4o slice, re-checked per tier).
- **H4 (best-of-N vs orchestration):** a best-of-N(P0) selector — N independent P0 samples,
  oracle/selector chosen downstream — is a **competitive baseline** for the orchestration
  premium at each tier; the orchestration arms must beat best-of-N(P0) at matched samples
  to justify their complexity. Plan headline N = 4.

## Design

- **Independent variable (the ONE allowed exception to the fixed gpt-4o backbone):**
  the generation **backbone**, swept low→high across a capability ladder.
- **Tiers (PTU/Azure, generated by `run_e9_scale_curve.py`):**
  - `gpt-4o-mini` (low) — Azure mini endpoint, ~$0.01/report.
  - `gpt-4.1` (mid) — PTU, ~$0.08/report.
  - `gpt-4o` (high) — **CORPUS ANCHOR**: `DEFAULT_MODEL=gpt-4o` on PTU the configured PTU deployment,
    the same backbone as the 248k-report corpus; re-generated here under the identical
    scaffold for a clean within-harness curve. $0 marginal (PTU). Logged `[CORPUS ANCHOR]`.
- **Tiers (local, GPU queue — NOT generated by this harness):**
  - `Qwen2.5-7B` (P9 base) and the E8 `DeepSeek-R1-Distill-Qwen-7B` (2025-01 vintage) supply
    the 7B/9B-class capability points already on disk.
  - `Qwen2.5-14B` via **llama.cpp GGUF Q4_K_M** (pattern `p17_scale_qwen25_14b`,
    `scripts/run_e8_vintage_14b_gen.py`, strict-greedy, n=90) supplies the **14B local
    capability point**. This is the prereg-required tier the original `.pyc` SKIPPED as
    GPU-blocked; the GGUF path resolves the OOM, so it is **recovered** here as a sequential
    GPU job (one model in 16 GB VRAM at a time), NOT a PTU/Azure cell. See §Divergences.
  - Combined ladder for the fit: **gpt-4o-mini → gpt-4.1 → gpt-4o** (Azure) **+ 7B + 9B +
    14B local** = up to 6 capability tiers.
- **Architectures (held FIXED across the sweep):** P0 (baseline), P1 (iterative RAG),
  P4 (perspective STORM). best-of-N is NOT a separate architecture: it is realised by
  `--best-of-n N` (N independent samples per (tier, arch) cell); best-of-N / selector /
  oracle are computed DOWNSTREAM from the N samples in the builder.
- **n:** 90 queries (`data/eval_queries_v2.json`, sorted by id), full eval set, per cell.
- **Cells:** tiers × arches; reports = cells × n × best-of-N.
  - Full Azure curve at N=4: 3 tiers × 3 arches × 90 × 4 = **3,240** generated reports.
  - The plan's "1,080 new runs" = 3 tiers × 4 arch-cells × 90 at N=1; N=4 multiplies the
    P0/cluster cells from which best-of-N is computed.
- **Decoding/determinism:** temperature 0 / strict-greedy; seed everything; sorted query
  ids; sorted cells; the backbone is encoded in the cell directory name
  (`e9_<tier>_<arch>[__s<k>]`) so judge ingestion and analysis read the IV off the dirname.
- **SEARCH_MODEL:** pinned to the corpus value `gpt-4o-mini` on EVERY tier; NEVER changed.

## Backbone-as-IV mechanism (consistency guarantee)

`run_e9_scale_curve.py` sets `os.environ["DEFAULT_MODEL"]=tier` (and pins SEARCH_MODEL)
BEFORE the first pattern import, purges `deep_research.config` and `deep_research.patterns.*`
from `sys.modules` so the backbone re-binds, lazily `importlib.import_module`s the pattern,
then HARD-ASSERTS the imported module's bound `DEFAULT_MODEL == tier` ("BACKBONE MISMATCH"
abort). This guarantees the chosen backbone propagates to source extraction, intermediate
reasoning, and final synthesis alike.

## Judge (authoritative + cross-check)

- **Authoritative judge:** GPT-5.2 (`JUDGE_MODEL=gpt-5.2`) on the cloud JUDGE Azure endpoint
  (never PTU, never Opus), via `scripts/run_gpt52_judge_namespaced.py` reading
  `JUDGE_RESULTS_BASE=results/experiments_e9_scale` (or via `--link-for-judging` symlink
  aliases under `results/experiments/<cell>`), writing verdicts ONLY to
  `--judge-out results/judge_gpt52_e9_scale`. The generation harness PRINTS this exact
  invocation and NEVER runs it.
- **Cross-check (non-authoritative):** gpt-4.1 MAY serve as a secondary cross-check
  EXCEPT on its OWN backbone arm (`e9_gpt-4.1_*`) — judge-independence rule. A Claude slice
  is optional. Neither is the authoritative score.
- **Rubric:** rubric_v2 (9 dimensions, weighted overall) — the same rubric as the corpus,
  so the gpt-4o anchor tier is directly comparable to the published numbers.

## Endpoints (pre-registered, computed by `build_e9_scale.py`)

1. **Benefit-vs-capability fit:** `Δ(arch, tier) = mean_score(arch, tier) − mean_score(P0, tier)`
   for arch ∈ {P1, P4}, fit against an ordinal capability index (and against the gpt-4o
   anchor's published score as a continuous capability proxy). Report slope sign + CI (H1).
2. **AdaptOrch convergence test:** between-arch score variance per tier; test that it is
   monotone non-increasing in capability (H2). Reference: AdaptOrch convergence law
   (arXiv 2602.16873), long-form regime.
3. **Matched-budget-per-tier control:** recompute (1) restricting to reports within a common
   per-tier token/cost budget band; report whether the lower-tier premium survives (H3).
4. **best-of-N(P0) baseline:** from the N=4 P0 samples per (query, tier), compute the
   oracle-best and a length-free selector; compare to the orchestration arms at matched
   samples (H4).

## Corpus safety (HARD)

- Generation writes ONLY to NEW roots: `results/experiments_e9_scale` (reports) and
  `checkpoints/e9_scale` (per-(cell,query) checkpoints). `resolve_safe_out()` HARD-REFUSES
  any root resolving to / inside / above the protected paths
  {`results/judge_gpt52`, `results/experiments`, `data/analysis`, `reports/eval_v2/verdicts`},
  and is robust to the `results/experiments → artifacts/experiments/canonical` symlink.
- `--dry-run` makes ZERO API calls and writes nothing. `--self-test` runs in-process checks.
- The canonical store is UNTOUCHED in the generation/build phase except by the dedicated
  `build_e9_scale.py` (atomic tmp+replace, append-only, NEW key `e9_scale_curve`, never clobber).

## Cost (pre-registered envelope)

- Generation: gpt-4o-mini @ $0.01 + gpt-4.1 @ $0.08 + gpt-4o @ $0 (PTU) over the swept cells.
  Full N=4 Azure curve ≈ $97 generation.
- GPT-5.2 judging @ $0.2/report dominates: full N=4 Azure curve ≈ $648 judging; the local
  14B point adds 90 reports ≈ $18. Plan §E9 budget line: ~$150 at the swept-cell granularity
  the plan scopes (P0/cluster cells only); the full 3×3×90×4 judging is the upper bound and
  is human-gated. **No paid run is launched in the build phase.**

## Divergences from the recovered `.pyc` (declared, not hidden)

- **14B tier recovered (the ONE deliberate correction).** The surviving `.pyc` SKIPPED the
  `Qwen2.5-14B-4bit-local` tier as GPU-blocked (4-bit transformers OOMs on the 16 GB RTX 5080
  at corpus context). That is now STALE: the llama.cpp GGUF Q4_K_M path runs the 14B on this
  exact card at ~76 tok/s. RESOLUTION: the 14B is **added back** to the capability ladder as a
  GPU-queue step (`run_e8_vintage_14b_gen.py`, pattern `p17_scale_qwen25_14b`), feeding the
  E9 curve as the local capacity point, restoring the full ladder the plan + headline (i)
  depend on. `run_e9_scale_curve.py` does NOT generate the 14B (it is a sequential GPU job,
  one model in VRAM at a time) — it logs the tier loudly and points at the GPU-queue step.

## Stopping / analysis rules

- Idempotent `--resume` (default ON): a completed (cell, query) checkpoint with
  `status=="success"` is skipped; `--no-resume` redoes it. Partial progress never re-spends.
- A cell with any judge gaps is judged with `--resume` until complete before the builder folds
  it in; the builder refuses to compute endpoints on incomplete tiers.
